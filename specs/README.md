# 规格驱动开发（SDD）

本项目采用轻量 SDD：**规格描述要交付的行为，代码实现规格，验证结果证明实现符合规格。** 暂不依赖某个特定 CLI 或外部规格管理工具。

## 文档分工

- `../约拍项目-MVP规格.md`：产品方向、MVP 范围和高层业务规则。
- `../约拍项目-开发计划.md`：阶段顺序、交付目标、技术决策和验收路径。
- `features/`：稳定的功能基线规格，是已确认功能行为的权威来源。
- `changes/`：正在讨论或实现的功能/行为变更，每项变更一份目录。
- `templates/change-template.md`：新变更的起始模板。
- `../docs/openapi/`：API 的机器可读契约；与功能规格互相引用，不能互相矛盾。

高层 MVP 文档不复制所有细节。功能基线逐步建立后，在 MVP 文档中链接到相应规格。

当前基线从 `features/mvp-baseline.md` 开始，记录已经确认的产品行为及仍然阻塞完整实现的资金规则。

## 一个功能的工作流

1. **识别变更**：确认用户目标、当前行为、目标功能、范围内/范围外事项及依赖。
2. **写规格**：在 `changes/<change-id>/` 编写 `proposal.md`、`spec.md`；涉及架构/关键取舍时补 `design.md`。每个要求分配稳定 ID，并写验收场景。
3. **标注待决项**：记录影响行为的未知数。若会改变资金、隐私、权限、取消责任或用户承诺，相关实现不得用假设补齐；可继续不依赖该决定的工作。
4. **拆任务**：在 `tasks.md` 列出有序、可独立验证的任务，覆盖前端、API、数据库迁移、OpenAPI、运营后台和验证（按实际影响选择）。
5. **实现**：按任务逐项完成；每个任务检查对应要求 ID。实现超出或偏离规格时，先更新规格并说明变更。
6. **验证**：按验收场景执行相关检查，记录命令/人工步骤和结果。不要声称未执行的检查已通过。
7. **归档**：功能完成后，将确认的行为合并到 `features/` 基线，摘要同步到 MVP/开发计划，标记任务完成并把变更目录移到 `changes/archive/`。

用户明确要求实现某功能，通常意味着可以按此流程继续起草并实现，不需要为例行文档步骤重复询问。若规格中出现需产品方决定的关键歧义，只询问受影响的部分。

## 规格写作约定

- Requirement ID 使用短域前缀，例如 `AUTH-01`、`PHOTO-01`、`AVAIL-01`、`BOOK-01`、`MSG-01`、`PAY-01`、`ADMIN-01`。
- 使用明确角色和条件描述行为，避免“友好”“快速”“合适”等不可验收词语；质量属性要给出可验证目标或明确标为后续决策。
- 验收场景使用 Given/When/Then，或同等清楚的前置条件、操作、预期结果。
- 同一要求不得同时出现在多个文件并出现不同表述。基线规格是已确认行为权威；变更规格在归档前是该变更目标的权威。
- 每项变更都注明状态：`draft`、`ready`、`in-progress`、`verified` 或 `archived`。

## 目录约定

```text
specs/
  README.md
  AGENTS.md
  features/                 # 已确认的功能基线规格
    AGENTS.md
  changes/                  # 当前规格变更
    AGENTS.md
    archive/                # 首项变更归档时创建
  templates/
    AGENTS.md
    change-template.md
```

首次有变更归档时创建 `changes/archive/` 目录，并在其中保留原变更规格和验证记录。
